## Approaches considered

1. **Selected: explicit short API function and separately retained runtime role.** Add one narrowly named Lambda runtime role through a new protected deployment-identities scope, then add its exact ARN and the Auth/API deployment roles to the Registry. Use an explicit short function name and exact IAM resources. This makes all principals known before the API change-set review and allows concrete policy simulation.
2. Create the runtime role inside the API stack with an explicit name. This avoids one identities-stack add, but the Registry would have to admit a principal that does not yet exist and the API change set would create its own read principal. It has fewer release stages but weaker staged proof of the reader boundary.
3. Widen wildcard IAM/Registry exceptions to tolerate generated names. This would include names outside the intended production function and risks admitting TEST identities. Reject.

The candidate names are `zlp-thn-auth-runtime-prod-role` and `zlp-thn-auth-runtime-production`. Read-only IAM, Lambda, Logs and CloudFormation checks found no collision on 2026-10-01. Recheck immediately before review and execute.
